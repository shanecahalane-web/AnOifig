# Phase 1 proposal and lane contracts

Status: approved implementation target and regression baseline. This contract is
not implemented by commit d0152dfb or by this milestone. Existing ADR 0006 and
ADR 0005 describe the current implementation; this document describes the
intended replacement for their conflicting mutation and scheduling behaviour.
No invoice issuance, tax decision or external delivery is authorised by it.

## Proposal lifecycle

The model proposes preparation-note changes; it never grants permission to
persist them. Existing schema, evidence and financial validators filter proposed
candidates, not authority. The application computes a complete immutable diff,
including additions, replacements and removals, from the saved notes and the
validated candidate. A no-op does not change version. A complete, bounded preview
and a challenge are generated by the application; an incomplete or oversized
preview fails closed and cannot be confirmed.

| Current state | Event | Next state | Canonical notes |
| --- | --- | --- | --- |
| none | valid nonempty proposal, matching captured version | pending | unchanged |
| pending | valid explicit confirmation after preview acceptance | confirmed | exact diff applied once |
| pending | explicit rejection | rejected | unchanged |
| pending | expiry | expired | unchanged |
| pending | newer proposal, reset or forget | superseded | unchanged except for the explicitly requested reset/forget |
| confirmed, rejected, expired, superseded | any later confirmation | same terminal state | unchanged |

There is at most one pending proposal per conversation. A newer proposal
supersedes the earlier proposal; its old confirmation cannot select the new one.
Unknown, stale or revoked confirmations leave both the state and canonical notes
unchanged. Rejection is an exact application-recognised command bound to the
proposal, not an AI inference. The entire inbound body must match `APPLY ` or
`REJECT ` followed by exactly 32 uppercase hexadecimal characters, with one ASCII
space and no additional whitespace or text. The application generates the
challenge from 128 cryptographically random bits. A pending proposal expires
24 hours after its application-recorded UTC creation time. Generic yes, quoted
text, appended instructions and model-generated consent are not confirmation.

The proposal binds tenant, authorised user, conversation, originating message,
proposal identity, expected notes version, immutable exact before/after diff,
expiry, challenge and its application-generated preview and outbox. Preview must
show the entire diff and disclose that no update has happened. Challenges and
proposal content are sensitive: do not log them, expose them through queue
gateways, or replay them as model history. Apply current member/role checks and
forced RLS, composite tenant/user/conversation relationships, least-privilege
grants, and existing bounded input and retention controls.

Confirmation is an exact application-owned inbound action handled before any
model call. In one transaction recheck active route and membership, user, tenant,
conversation, proposal, challenge, pending status, expiry, expected version and
the immutable before/after values. Consume the proposal, apply exactly the diff,
increment the notes version once, mark the inbound handled, and record audit and
one durable reply/outbox atomically. Duplicate provider SID, repeated delivery,
concurrent confirmations, lost commit acknowledgement and replay cannot produce
another mutation or another reply for the same message. A wrong identity, stale
version, wrong challenge or altered diff never becomes a grant. Confirmation of
preparation notes is never authorisation to issue an invoice.

The preview must have an accepted provider send or a signed callback reconciling
acceptance and must not already have a known failed, canceled or undelivered
message status. When its dispatch is still in flight or uncertain, defer the
confirmation without a model call or retry failure count until resolution or
expiry. A definitively failed/blocked preview cannot be confirmed. Acceptance
does not prove the user read the preview; a later failure callback is possible.
Existing safe retry and uncertain-send rules remain authoritative.

## Conversation lanes and recovery

Each conversation has independent ordered inbound and outbound lanes. Source
acceptance order is assigned monotonically under the conversation lock; replies
inherit their source order. This does not reconstruct a sender order which
arrived at the provider or ingress out of order. Only the earliest unresolved
head of a lane may perform its next normal business operation; at most one such
operation is active per lane. Future-due, parked and uncertain heads block their
own successors. Inbound can advance while outbound awaits uncertain delivery.
Unrelated conversations and tenants remain runnable.

Discovery and atomic claim select eligible heads fairly; a claimed receipt does
not itself authorise domain writes. Recheck head, route, state and fencing under
lock. Claim at most one job per synchronous execution slot, with dedicated inbound
and outbound capacity so a slow model does not consume all reply capacity.
Claims, abandoned receipts and cooldowns are not committed progress. A source
that is due for terminal recovery remains discoverable without allowing a
successor to send out of order. A callback, completion, lease expiry, due retry
or authorised operator resolution must make the next eligible head discoverable;
periodic database discovery is the durable fallback after crashes.

Existing opaque receipt settlement cannot release a newer claim. Reuse durable
run token/version/deadline fencing for model calls and durable dispatch attempt,
lease and state fencing for Twilio calls. Stale completions must not mutate newer
state. Record send intent before provider I/O; never automatically resend an
uncertain send. Signed callbacks and authorised operator reconciliation resolve
uncertainty. No provider I/O holds a database transaction open. Lock ordering must
be explicitly consistent: conversation before relevant source/run/proposal or
outbox/message; callbacks that lock outbox then message must not later acquire
the conversation lock. Preserve 24-hour window, bounded retries and idempotent
source/reply/outbox constraints.

Any new sequence backfill, source trigger or content-free SECURITY DEFINER gateway
requires a reviewed forward migration, forced RLS, narrowly scoped privileges,
fixed search_path, and real restricted-role PostgreSQL tests. Migration must
preserve durable source order and legacy unsourced replies, or stop for operator
reconciliation; stop old workers before migration and never mix ordering schemes.

## Regression baseline and exit

`tests/integration/test_phase1_contract_regressions.py` contains strict expected
failures against the current code: unsafe persistence, unimplemented confirmation
flow and predecessor-unaware queue claims. Expected failure means a known unmet
contract, not a passing safety gate. An unexpected pass is a failure so the test
must be inspected and converted to an ordinary passing assertion when the feature
is implemented. Confirmation tests cannot reach their final checks until pending
proposal creation exists; their expected failure explicitly records that missing
prerequisite. Existing stale model-completion, tenant isolation, replay and receipt
fencing tests are independent controls, not evidence that confirmation exists.

Milestone 1 is complete when these contracts, deterministic fixtures and the
baseline results are committed, and relevant tests run with genuine restricted
PostgreSQL. The resulting branch is a test baseline, not a merge or staging
approval: expected failures must be resolved in later milestones.
